Terms used on this page

  • The data hub ("the hub" on this page): the data layer this page describes, owned by data engineering. It is not the Agentic Hub, which is the AI platform the components belong to.
  • The components: the Agentic Hub's AI services: the Clinical Abstractor, the Symbolic Auditor and policy-to-logic.
  • The two doors: the Lookup API (codes and reference data) and the Explain API (why this code).
  • Plumbing: the platform-specific parts: triggers, file ingestion, catalog, roles, deployment.

Part 1 — Decision tenets and how we choose a platform

Why this page

There is no perfect platform; every option has cons. So before we compare Databricks, AWS-native or GCP, we write down what the data hub must guarantee, and what we are willing to trade. The guarantees come from the requirements (audit, PHI, evaluation, the CIS contract), not from tool preference.

The tenets are must-haves on any platform. The comparison further down is about how much each platform gives us out of the box, and how much we would have to build ourselves.

Tenets — what the hub must guarantee, on any platform

These are design commitments, not a description of what is built. Part 2 shows what exists today.

  1. Nothing that feeds a decision is ever lost or overwritten. Bronze, the truth graph and gold are append-only: a rerun adds a version, a correction adds a row. Silver holds the latest copy of each chart and can be rebuilt from bronze for any earlier version.
  2. Every decision can be reproduced. Each gold row records the versions that produced it: rule snapshot and rule fingerprint, truth graph, model, CCDM, taxonomy, HCC model, NLP and feed. Re-running the Symbolic Auditor on the stored truth graph and rule snapshot gives the same answer. Reproducing the AI steps before it, from bronze, is the target and depends on those components being repeatable.
  3. Every piece of evidence has a source. A code points to a truth graph fact; the fact carries its evidence sentence with page and position; that points back to the original ZIP in bronze. The rule points to its PRM snapshot and guideline page. Nothing is guessed at audit time.
  4. PHI is read by jobs, not people. Our jobs and the Explain API read PHI tables. People work through governed, masked views; unmasked access is limited to named roles and logged.
  5. Other systems come through the doors. The components use handoff files for the first end-to-end run (proposed) and the two doors later; CIS uses S3 files and the Explain API. No other system reads our tables directly. We never write to PRM; PRM is the store of record for rules and we keep a copy.
  6. Same facts plus same rules give the same answer, and a rule change flips no previously-correct chart without review. Both are checked against the golden dataset on every rule promotion and release.
  7. Bad data is kept and reported, not silently dropped or corrected. A row that fails a check goes to quarantine with a reason and an owner, and is left out of what goes downstream. The counts go back to CIS as a daily number.
  8. The data layer is portable; only the plumbing is platform-specific. Tables are in open formats (Delta or Iceberg) on object storage, jobs are PySpark, paths and endpoints are configuration.

Trade-offs we are prepared to accept

  • A rebuild of the plumbing if the company's hyperscaler decision moves us; not a rebuild of the data layer.
  • A file handoff with the components for the first end-to-end run, instead of APIs (proposed; to confirm with the Agentic Hub team).
  • Some lead time for cross-account access and PHI approval, in exchange for each team keeping its own bucket and workspace.
  • The hub measures and reports data quality; it does not correct source data.

This is the inventory of every kind of data in the data hub. One row per kind. For each: what it is in plain words, who writes it, who reads it, whether it holds PHI, how long we propose to keep it, and where we are today.

Status: built = runs today on synthetic data · next = designed, not started; the order depends on PRM, CIS and the components · later = not scheduled.

The tenets in Part 1 apply to every row.

Read by: where a person or team is listed as a reader of PHI data, they read it through masked views (tenet 4). The exception is the audit package, which goes unmasked to the named audit roles.

How it is organized

Every table will be registered in the catalog with an owner, a PHI flag, a retention period. One schema per lane: bronze, silver (ccdm), truth graph (ctg), gold, policy, reference, feedback.

The audit question, walked through

"Why did you recommend E11.22 on this chart in 2026?"

Gold row (disposition, which check, confidence) → the rule and rule snapshot → the rule text and guideline page (PRM's files, found through the policy copy) → the truth graph version, which carries the evidence sentence, page and position → the original ZIP (bronze). Gold, the truth graph and bronze are kept as versioned rows; silver is rebuilt from bronze when needed. The audit package is this walk, frozen into one file.
